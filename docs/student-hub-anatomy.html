Studenthub_Nov · SAP CAP + UI5

Student Hub, end to end

A student administration app. A SAPUI5 front end talks OData V4 to a Node.js CAP back end. The back end stores students, courses and enrollments in a database, and reads Business Partners live from an S/4HANA sandbox.

SAPUI5 1.120+OData V4@sap/cds 10SQLite (dev) / HANA (prod)XSUAA + App Router

The big picture

There are three runtime pieces: the browser app, the CAP server, and the data sources behind it. In production an App Router sits in front and handles login and routing. In local development cds watch plays all of those roles in one process.

Why there are two index.html files

They have different jobs, and only one of them ships to the cloud.

How a click becomes a backend call

Each action button maps to one OData operation. The URL is built from the selected row's ID, so the server knows which student the action is for.

  participant R as App Router
  participant S as StudentService (student-service.js)
  participant D as Database
  U->>V: opens ⋯ menu on a row, picks "Suspend"
  V->>C: press="onToggleSuspend"
  C->>C: read row via getBindingContext().getObject()
  C->>R: GET /odata/v4/student/$metadata (fetch CSRF token)
  R->>S: forwards with login token
  S-->>C: x-csrf-token header
  C->>R: POST /odata/v4/student/Students(1111…)/StudentService.suspendStudent
  R->>S: matches route ^/odata/v4/(.*) and forwards
  S->>S: check roles, run on('suspendStudent') handler
  S->>D: SELECT student, UPDATE status = Suspended
  D-->>S: updated row
  S-->>C: 200 JSON
  C->>C: MessageToast "Student suspended", model.refresh(), KPI tiles reload
  C->>R: GET /Students (table reloads)

Back end (CAP)

CAP turns each service in srv/*.cds into an OData V4 endpoint. The .cds file declares what exists (entities, actions, who may call them). The matching .js file supplies the logic through this.on(...).

Handler pattern

Almost every bound action in student-service.js follows the same steps, which is why the file reads like a recipe:

this.on('suspendStudent', 'Students', async (req) => {
  const { ID } = req.params[0];                 // key from the URL
  const student = await SELECT.one.from(Students).where({ ID });
  if (!student) return req.reject(404, ...);    // validate
  if (student.status === 'Graduated') return req.reject(409, ...);
  await UPDATE(Students).set({ status: 'Suspended' }).where({ ID });
  return SELECT.one.from(Students).where({ ID });   // return fresh row
});

The front end's callStudentService reads the error.message from a rejected response and shows it as a toast, so these messages are what the user sees.

S/4HANA connection

The Business Partners screen never talks to S/4HANA directly. It calls DavidS4Service, which forwards the request through CAP's remote service client. That keeps the API key on the server.

sequenceDiagram
  autonumber
  participant UI as BusinessPartners.controller.js
  participant CAP as DavidS4Service
  participant X as cds.connect.to('API_BUSINESS_PARTNER')
  participant S4 as sandbox.api.sap.com (S/4HANA Cloud)
  UI->>CAP: GET /DavidBusinessPartners?$top=50
  CAP->>CAP: on('READ') returns s4.run(req.query)
  CAP->>X: translate CQN to OData V2
  X->>S4: GET A_BusinessPartner?$top=50 + APIKey header
  S4-->>X: OData V2 JSON
  X-->>CAP: rows
  CAP-->>UI: OData V4 JSON {value:[...]}
  UI->>UI: bp model gets /partners, table renders

Because the entity is a projection on an external service, it has no database table. That is why the service needs its own on('READ') handler. Without it, CAP would try to read a table that does not exist.

Security and roles

In production, XSUAA issues a login token. The App Router forwards it and CAP checks the user's roles against @requires and @restrict. In development the same roles come from mocked users in package.json.

  participant AR as App Router
  participant X as XSUAA
  participant S as CAP (xssec)
  B->>AR: GET /studenthub/index.html
  AR-->>B: 302 redirect to XSUAA login
  B->>X: sign in
  X-->>AR: authorization code, then JWT
  AR-->>B: session cookie
  B->>AR: GET /odata/v4/student/Students
  AR->>S: forwards request + JWT
  S->>S: validate token, map scopes to roles
  S-->>B: data, or 403 if role missing
RoleLocal dev userRole collection (cloud)Inherits
UserVenkat, DavidUser (Studenthub_Nov …)read access, average credits
ManagerKaushalManager (…)User scope as well
AdminNagarjunaAdmin (…)Manager and User scopes

The service has @requires: ['User','Manager','Admin'], so anyone with one of those roles may call it. Inside, Students grants READ and getAverageCredits to User, and everything to Admin. graduateStudent needs Manager or Admin. deleteStudent needs Admin.

The UI shows every button to everyone. A User who presses Delete gets a 403 and the error appears as a toast.

Findings and tips

API key is stored in package.jsonThe S/4 sandbox APIKey is written in plain text under cds.requires and is committed to git. Move it to an environment variable or a .cdsrc-private.json that is git-ignored, and rotate the key.
Name is limited to 20 charactersStudent.Name is String(20). The create/edit dialog now stops input at 20 characters, but names such as "Venkatasubramanian Iyer" still cannot be stored in full. Raise the length in db/schema.cds (and the input's maxLength) if you expect long names.
Manager is not in the Students @restrictThe entity grants only User and Admin, while graduateStudent asks for Manager or Admin. Test with the Kaushal user to confirm a Manager can graduate a student. If not, add a grant for Manager.
UI does not hide buttons by roleEveryone sees Delete and New Student. The server rejects them correctly. If you want a cleaner experience, expose the user's roles to the UI and bind visible on those buttons.
OData V4 models need operationMode: "Server"Without it, any table with a sorter or a .filter() call fails with "Unsupported operation mode" and the page stays blank. Both V4 models in manifest.json set it.
Use targetType: 'any' in V4 expressionsWith the V4 model, ${status} inside {= … } is first converted to the control property's type (e.g. boolean for enabled) and throws. Write ${path: 'status', targetType: 'any'}.
The .deploy folder is a copymta.yaml refreshes it on every build. Edit files under app/studenthub only.
Good habits already in placeServer-side validation with clear HTTP codes, bound actions keyed by the row ID, one shared service helper with a CSRF token fetch before writes, all UI texts in i18n, and the S/4 key kept behind the CAP server instead of in the browser.
